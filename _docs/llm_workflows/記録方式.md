# 記録方式

このディレクトリは、`codex-rs` で動いている LLM ワークフローを「実装し直せる粒度」で記録するための置き場にする。

## ルール

1. ワークフローごとに 1 ファイルに分ける。
1. 本文は日本語で書く。
1. 先頭に YAML frontmatter を置き、少なくとも `prompts` と `call_points` を残す。
1. prompt が structured output を要求する場合は、該当 prompt の frontmatter に `schema` を書き、出力の形を記録する。
1. ここでいうワークフローは、LLM 実行や prompt/materialization を含む、意味のある処理のまとまりを指す。単なる値の代入、状態フラグの更新、単発の条件分岐だけではワークフローにしない。
1. 本文には必ず次の 3 点を入れる。
   1. 視覚的に分かるワークフロー図
   1. 各プロンプト資産の役割の説明
   1. Python での疑似コード
1. 図で `LLM:` と書くのは、サーバーへ request を送る境界だけにする。
1. prompt 資産そのものは、材料化された後の `context:` として扱う。

## frontmatter の書き方

### `prompts`

- ワークフローで実際に積まれる prompt 資産を列挙する。
- ここに書くのは、実際に LLM に渡る prompt 本文だけにする。
- `SKILL.md`、plugin / app / persona の注入元は context として別に扱い、`prompts` には入れない。
- 挿入時に追加される説明テンプレートがある場合だけ、その追加説明部分を prompt として扱う。
- 固定プレフィックスや出口用の固定文は prompt ではないので、`prompts` には入れない。
- `name` に相当するキーは、そのワークフロー内で追跡しやすい短い名前にする。
- `path` は実装上の参照元を示す。
- `description` は「最低限これだけを指示すれば動く」というレベルの要約にする。
- structured output を要求する prompt だけ、`schema` に JSON 形状を追記する。

### `call_points`

- ワークフローが実際に発火する箇所や、prompt fragment を materialize する箇所を書く。
- `path` は呼び出し元のファイルを示す。
- `line` は入口に近い行番号を 1 つ書く。
- `description` はその call point が何を起こすかを短く書く。

### `commands`

- ワークフローを起動するコマンドや、起動相当の入口を書く。
- `path` はコマンド処理の実装元を示す。
- `description` は「どの操作がこのワークフローにつながるか」を短く書く。
- 明示コマンドがないものは、`implicit` として自動発火の起点を書く。

## 本文の構成

おすすめの順番は次の通り。

1. `## 目的`
1. `## 全体像`
1. `## プロンプトの分解`
1. `## 疑似コード`
1. `## 実装時の注意`

### `## 全体像` の役割

- ここは入力の羅列ではなく、LLM 実行や prompt 更新の処理フローを書く。
- 図は「何がトリガーで、何が生成され、どこに返るか」が分かるようにする。
- 入力や出力は `## 入出力` に置き、`## 全体像` では状態遷移・分岐・再試行・確定の流れを示す。
- `全体像` の主語は、各ワークフローの「処理のループ」または「状態遷移」でなければならない。単なる setter や値の詰め替えはここに置かない。
- 図の入口は `turn_context` か、そのワークフローの turn 相当のコンテキストを起点にし、入力だけの一覧にしない。
- 図のノードは、prompt 生成・context 反映・履歴確定・LLM request のいずれかを表す。
- 図のノードは、`[<LLM:...>]` または `[<context:...>]` で始める。
- 複数の context を載せるときは `[<context:A+B+C>]` のように `+` でつなぐ。

## 図の書き方

Mermaid の `flowchart` か `sequenceDiagram` を使う。  
そのワークフローで「誰が何を積み、どの条件で分岐するか」が一目で分かれば十分。

## 疑似コードの書き方

- Python で書く。
- 実装の厳密な構文ではなく、制御フローが読めることを優先する。
- 1 回の入力から 1 回の出力までの流れを、関数単位で再現する。
- 変数名は `workspace` / `config` / `*_context` を基本にして、実装の内部構造をそのまま写さない。
- 関数名は `call_llm(...)` / `call_*_workflow(...)` / `build_*_context(...)` のように、役割が分かる抽象名にする。
- 別のワークフローを呼ぶときは `call_xx_workflow(...)` の形で書いてよい。ただし、状態更新や部分処理には使わず、ワークフローの入口にだけ使う。
- 状態変更を表す関数名は `update_xx(...)` に統一する。`mark` / `apply` / `set` は役割名として分けない。
- Rust の関数名や型名をそのまま並べるのではなく、処理の順序と境界が分かるように再構成する。
- `workspace.agents_md` のように、文脈の供給元は擬似コード上でも具体的に示してよい。

## プロンプトの見方

各ワークフローの `## プロンプト要約` は、prompt 資産の本文だけを短く要約する。

- `prompt` ごとに小見出しを分けて、その prompt 本文に何が書かれているかを 2-4 行で要約する。
- `AGENTS.md`、`SKILL.md`、plugin / app / persona の注入元、実行 context の説明はここに混ぜず、別の節に分ける。
- `prompt` 要約では、挿入された追加説明そのものを内容として書く。どこから来たかは書かない。
- 複数の文脈を積む場合は `[<context:A+B+C>]` のようにまとめて書き、本文ではその役割を説明する。
- `LLM:` は prompt の中身ではなく、その prompt をサーバーへ送る request 境界として使う。

## コンテキストの見方

- `AGENTS.md`、`SKILL.md`、plugin / app / persona の注入元は、LLM に渡る前の context として記録する。
- context は prompt 本文とは別に、どの情報が追加・反映されたかを示す。
- 追加説明テンプレートがある場合は、その部分だけを prompt として切り出して記録する。
